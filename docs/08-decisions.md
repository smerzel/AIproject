# 08 — למה נבחר כל פתרון

כל סעיף הוא החלטה אחת: מה היו האפשרויות, מה נבחר, ולמה.

## נושא המערכת

- **אפשרויות:** טיסות, חדשות, ארגון אירוע, גיוס.
- **נבחר:** גיוס מועמדים.
- **למה:** הדרישות עצמן מדברות על משרות: לוח של משרות פתוחות ומספר נרשמים, התאמת מועמד למשרה, וסוכן שמעריך מועמד. נושא אחר היה סותר אותן.

## מסד הנתונים בענן

| אפשרות | יתרון | חיסרון |
|---|---|---|
| **Somee (MS SQL)** | מומלץ בהוראות, חינם, SQL עם טרנזקציות | שטח קטן בחינם, לפעמים איטי |
| Azure SQL | מקצועי ומהיר | דורש כרטיס אשראי, הקמה מורכבת |
| Supabase (PostgreSQL) | מודרני ונוח | לא מה שהקורס ממליץ |
| MongoDB Atlas | חינם וגמיש | בלי טרנזקציות וסדר קבוע כמו SQL, וזה הכי חשוב ל-Event Sourcing |

- **נבחר:** Somee.
- **למה:** הקורס ממליץ על Somee גם למסד וגם לשמירת האירועים. יומן אירועים צריך סדר קבוע וכתיבה בבת אחת, ו-SQL נותן את שניהם. קבצי קורות החיים לא נשמרים במסד, רק הטקסט, כך שהשטח מספיק.
- **בנוסף:** SQLite מקומי לפיתוח ולבדיקות בלבד. אותו קוד, ומחליפים ב-`DATABASE_URL`.

## החיבור ל-SQL Server

- **אפשרויות:** `pyodbc` (דורש התקנת ODBC Driver של מיקרוסופט במערכת וב-Docker), `pymssql` (התקנה ב-pip בלבד).
- **נבחר:** `pymssql`.
- **למה:** פחות התקנות ופחות נקודות כשל, במיוחד ב-Docker.

## כתיבה למסד: משפט SQL גלוי

- **אפשרויות:** SQLAlchemy ORM, SQL ישיר עם מתאם קטן (`app/db.py`).
- **נבחר:** SQL ישיר.
- **למה:** ב-Event Sourcing רוצים לראות בדיוק מה נכתב: `INSERT` ליומן ואז עדכון פרויקציה. ORM מסתיר את זה. המתאם מתרגם `?` ל-`%s` כדי לתמוך גם ב-SQLite וגם ב-MS SQL.

## איפה נשמרים האירועים

- **אפשרויות:** EventStoreDB, Kafka, טבלת `events` באותו מסד.
- **נבחר:** טבלת `events` ב-Somee.
- **למה:** הקורס דורש שכל שינוי יישמר כאירוע, בענן (Somee). מערכת נפרדת לאירועים לא רצה על Somee ומוסיפה שרת.

## מתי מתעדכנות טבלאות המסכים

- **אפשרויות:** סינכרוני (מיד אחרי `append`), אסינכרוני (תהליך שמאזין לאירועים).
- **נבחר:** סינכרוני.
- **למה:** המשתמש רואה את השינוי מיד. אסינכרוני מוסיף תור ועיכוב בלי תועלת בגודל הזה. `app/replay.py` עדיין מוכיח שאפשר לבנות הכל מחדש מהאירועים.

## איפה נשמר החיפוש לפי משמעות

| אפשרות | יתרון | חיסרון |
|---|---|---|
| **Chroma** | חינם, מקומי, בלי חשבון, סינון לפי metadata | לא בענן |
| Pinecone | בענן | חשבון ומפתח, עוד שירות שהרשת עלולה לחסום |
| FAISS | מהיר מאוד | בלי סינון לפי משרה, הכל ידני |
| pgvector | בתוך PostgreSQL | אנחנו על MS SQL |

- **נבחר:** Chroma.
- **למה:** הקורס דורש להפוך את קורות החיים לחיפוש לפי משמעות, ולא דורש שענן ישמור את זה. צריך לסנן לפי משרה, ולשמור גם את המסמך המלא וגם קטעים, בשביל הדירוג ובשביל הציטוטים בדוח.

## המודל שהופך טקסט למספרים

- **אפשרויות:** Gemini/OpenAI embeddings (מפתח, רשת, עלות), `nomic-embed-text` ב-Ollama, `all-MiniLM-L6-v2`.
- **נבחר:** `all-MiniLM-L6-v2` (ONNX, מובנה ב-Chroma).
- **למה:** חינם, מקומי, 384 ממדים, בלי מפתח. נמדד: CV מתאים 0.62 מול CV לא קשור 0.06.

## ספריית הסוכן

- **אפשרויות:** LangChain `deepagents`, Google ADK, LangGraph רגיל, CrewAI.
- **נבחר:** `deepagents`.
- **למה:** הקורס דורש Deep Agent, וזו הספרייה בשם הזה. יש בה תכנון וחלוקה לעוזרים. בגרסה הראשונה הייתה Google ADK, והוחלפה.

## מבנה הסוכן

- **אפשרויות:** סוכן יחיד עם 4 כלים, מתזמר עם תתי-סוכנים.
- **נבחר:** מתזמר + `cv-analyst` + `web-researcher`.
- **למה:** זה מה שמבדיל Deep Agent מסוכן רגיל. כל תת-סוכן מקבל רק את הכלים שלו, וההקשר שלו נפרד. בדוח רואים מי עשה מה.

## מודל השפה

| אפשרות | יתרון | חיסרון |
|---|---|---|
| **Gemini 2.5 Flash** | מהיר (כ-2.5 דקות להערכה מלאה), חכם, חינם | דורש אינטרנט ומפתח |
| **Ollama `qwen2.5:3b`** | מקומי, חינם, בלי אינטרנט, מופיע בתרשים הקורס | על מעבד בלי כרטיס מסך: יותר מ-10 דקות להערכה |
| OpenAI / Claude | חזקים | בתשלום |

- **נבחר:** `LLM_PROVIDER=auto`: Gemini ראשי, Ollama גיבוי.
- **למה:** במחשב הפיתוח (i7-1355U, 16GB, בלי GPU) Ollama לא סיים הערכה ב-9 דקות. הגיבוי מבטיח שהמערכת ממשיכה לעבוד בלי אינטרנט או כש-Gemini נכשל.

## חיפוש באינטרנט

- **אפשרויות:** Tavily, Google Custom Search, SerpAPI, Brave Search.
- **נבחר:** Tavily.
- **למה:** מוזכר בהוראות, יש לו שרת שהסוכן מפעיל, והוא מחזיר תוכן מוכן ולא רק קישורים. 1,000 חיפושים בחודש בחינם.

## שירות חיצוני שהסוכן מפעיל

- **אפשרויות:** Tavily, Gmail ("כגון": מספיק אחד).
- **נבחר:** שניהם. Tavily לסוכן ההערכה, Gmail למייל ההחלטה למועמד.
- **למה:** הסוכן צריך את Tavily ממילא. Gmail משלים את החלטת הגיוס: ההחלטה צריכה להגיע למועמד, וזה שירות חיצוני שני שהסוכן מפעיל.

### איך מתחברים ל-Gmail

| אפשרות | יתרון | חיסרון |
|---|---|---|
| **שרת Gmail MCP קיים עם OAuth** (`@gongrzhe/server-gmail-autoauth-mcp`) | שרת MCP אמיתי של Gmail, כמו שהדרישה מנסחת; Gmail API רשמי; בלי סיסמה בקוד; אותו מנגנון stdio כמו Tavily | הקמה ב-Google Cloud (פרויקט, Gmail API, מסך הסכמה, משתמשת בדיקה); התחברות חד-פעמית בדפדפן; באפליקציה במצב Testing ה-token פג אחרי 7 ימים |
| שרת MCP משלנו מעל SMTP עם App Password | הקמה של 5 דקות, בלי Google Cloud | זה כבר לא "Gmail MCP" אלא SMTP שעטפנו; דורש אימות דו-שלבי בחשבון וסיסמת אפליקציה ב-`.env`, שנותנת גישה מלאה לחשבון; עוד קוד לתחזק ולבדוק |

- **נבחר:** שרת Gmail MCP עם OAuth, גרסה נעוצה `1.1.11`, מותקן בתמונת ה-Docker.
- **למה:** הקורס מבקש שהסוכן יפעיל שירות חיצוני, ושרת קיים מוכיח את זה טוב יותר מעטיפה שכתבנו. התחברות עם הרשאה מוגבלת עדיפה על סיסמה ששמורה בקובץ. הקוד מזהה הצלחה לפי הטקסט `Email sent successfully with ID`, כי השרת מחזיר שגיאות כטקסט רגיל. לכן הגרסה קבועה.
- **איפה שולחים:** ב-worker, לא בבקשת ה-HTTP. שליחה כוללת הפעלת תהליך Node ורשת, ובתוך POST היא הייתה מעכבת את ה-HR ושוברת את ההפרדה. ה-view רק רושם את ההחלטה.
- **process נפרד ל-notifier מול שלב ב-worker:** נבחר שלב באותה לולאה של `agent.worker` (הקוד ב-`agent/notifier.py`, שאפשר גם להריץ לבד). קונטיינר נוסף היה מוסיף עוד תהליך Python עם אותה תמונה כבדה בשביל כמה מיילים ביום.
- **התחברות חד-פעמית:** בתוך הקונטיינר (`scripts\gmail_auth.ps1`), כי `npx` על Windows נכשל כאן בגלל שם תיקיית משתמש בעברית. שרת ההתחברות מאזין לכל הממשקים בפורט 3000, ולכן `-p 3000:3000` מספיק כדי שה-redirect ל-`localhost:3000` יגיע אליו.

## שני הכלים שקוראים קורות חיים

- **נבחרו:** `extract_resume_profile` (כישורים, שנות ניסיון, מעסיק אחרון) ו-`evaluate_requirement_coverage` (כמה מהדרישות מכוסות).
- **למה:** הסוכן משתמש בשניהם בפועל. הם דטרמיניסטיים ולכן נבדקים בבדיקות, והם מקור הציונים, לא המודל.

## הסוכן רץ בתהליך נפרד

- **אפשרויות:** Celery + Redis, cron, תהליך שקורא את המסד כל N שניות.
- **נבחר:** `agent.worker` שקורא את המסד כל 20 שניות.
- **למה:** הקורס אומר שהסוכן יקרא רשומות ממסד הנתונים, וזה בדיוק מה שהוא עושה. אין צורך בשירותים נוספים.

## צורת הממשק

- **אפשרויות:** React SPA + REST API, Flask + Jinja.
- **נבחר:** Flask + Jinja + Bootstrap RTL.
- **למה:** הקורס מבקש שהמסך יהיה נפרד מהכתיבה ומהקריאה. תבנית Jinja היא המסך. פרויקט אחד, פחות חלקים.

## התחברות

- **אפשרויות:** JWT, Flask-Login, session של Flask.
- **נבחר:** session של Flask, סיסמה מוצפנת ב-`werkzeug.security`.
- **למה:** JWT מתאים ל-API ולמובייל. לאתר שמרונדר בשרת, session הוא הסטנדרט.

### שתי דלתות

- **מה אתרים עושים:** Indeed מפריד כניסת מעסיקים (Employer Dashboard) מכניסת מחפשי עבודה, ונותן לכל איש צוות תפקיד. Greenhouse מפריד פורטל מועמדים ממערכת הגיוס, ומשרה לא נפתחת לפני אישור.
- **נבחר:** דלת מועמדים ודלת מגייסים, עם הרשמה עצמית בשתיהן. בדלת המגייסים בוחרים מגייסת או מנהל גיוס. כל דלת עוצרת חשבון מהסוג השני.
- **למה:** כל תפקיד מקבל סמכות משלו, כמו שכתוב בכניסה למערכת ב-[מה המערכת עושה](04-features.md): מגייסת כותבת ומחליטה, מנהל גיוס מאשר פתיחה. כך שלושת התפקידים שונים באמת. במערכת אמיתית הרשמת צוות הייתה בהזמנה. כאן ההרשמה פתוחה כדי שהבוחן יוכל לנסות כל תפקיד.

### כניסה עם Google

- **אפשרויות:** לממש OAuth ידנית ב-`httpx`, Flask-Dance, Authlib.
- **נבחר:** Authlib (`app/google_auth.py`), OpenID Connect עם `openid email profile`, לצד הסיסמה.
- **למה:** Authlib בודק את ה-`state` וה-`nonce` ואת חתימת ה-ID token. גוגל מחזיר אימייל ושם, לא תפקיד. לכן התפקיד נשמר ב-session החתום לפני היציאה לגוגל: דלת מועמדים תמיד `candidate`, דלת מגייסים רק `hr` או `hiring_manager`. אימייל שלא אומת נדחה. משתמש קיים נכנס לחשבון שלו, וחשבון חדש נרשם דרך `UserRegistered` עם `auth_provider=google`.
- **בלי מפתחות:** אם `GOOGLE_CLIENT_ID` או `GOOGLE_CLIENT_SECRET` ריקים, הכפתור לא מוצג והנתיב מחזיר 404. זה חיבור נפרד מ-Gmail MCP, שמשמש רק לשליחת מייל החלטה.

## הרצה ב-Docker

- **נבחר:** `docker compose` עם `web` ו-`worker` מאותה תמונה, volumes משותפים ל-Chroma ולקבצים.
- **למה:** מפריד את הסוכן לתהליך עצמאי, כמו שהקורס דורש, ומריץ הכל בפקודה אחת.

## מתכון Flask מהאתר skills.sh

- **נבחר:** `flask-python` (`npx skills add mindrally/skills`).
- **למה:** מתאים בדיוק לשרת: blueprints, application factory.

## בדיקות ב-GitHub

- **נבחר:** GitHub Actions עם שלוש משימות: `sqlite`, `sql-server` (SQL Server 2022, אותו מנוע כמו Somee), `docker build`.
- **למה:** מוכיח שהקוד עובד גם על מכונה נקייה וגם מול MS SQL, בלי תלות ברשת הביתית.

## עומק הסינון וההרשאות

- **הרשמה מהאתר:** הוחלף בסעיף "שתי דלתות" למעלה. דלת המועמדים יוצרת רק מועמד, ודלת המגייסים יוצרת מגייסת או מנהל גיוס. `seed_demo.py` עדיין יוצר את חשבונות הדמו דרך אותה כתיבה.
- **ציון רשת:** מחושב ב-`_finalize` מהקישורים שחזרו, לא מהמספר שהמודל כתב.
- **רשת:** Tavily מחפש את השם המלא (לא את הקישור מה-CV ולא את הטכנולוגיה). GitHub נבדק כתיק: מאגרים ושפות מול המשרה, לא כאימות שהכתובת קיימת. לינקדאין נשמר כקישור בלבד.
- **כיסוי דרישות:** התאמה של מילה שלמה, כדי ש-Java לא ייספר בתוך JavaScript.
- **מסד:** חיבור אחד לבקשת דפדפן, אינדקס ייחודי על `(aggregate_id, version)`, והאירוע וההקרנה נשמרים באותה טרנזקציה.
- **Gmail:** נשאר מחוץ לסיבוב הזה. הקוד שולח רק אחרי חיבור OAuth.

## מה הדוח מראה על עבודת הסוכן

- **אפשרויות:** להחליף את Deep Agent ב-LangGraph כדי לקבל State מובנה, או לבנות את אותו State מתוצאות הכלים אחרי הריצה.
- **נבחר:** להשאיר את `deepagents` ולבנות `agent_state` ב-`_finalize`.
- **למה:** ההגשה דורשת Deep Agent. מצגת 7 מבקשת להראות תוכנית, צעד, קריאות כלים, ציטוטים וביטחון. אלה נגזרים מהכלים שרצו בפועל, כך שהמסך לא מציג תוכנית שהמודל המציא. `confidence` הוא הציון הכולל מהכלים. כל כישור חובה מגיע עם המשפט מקורות החיים, או בלי ציטוט אם לא נמצא.
